## Abstract

[EIP-5792](./eip-5792.md) defines a JSON-RPC API for communication between wallets and dApps, and lets the API be extended with "capabilities".

This proposal defines capabilities that a wallet can implement to expose the features of an [EIP-8141](./eip-8141.md) frame transaction to dApps: a time limit on validity, keyed nonces ([EIP-8250](./eip-8250.md)), a paymaster, partial atomic batching, gas limit and fee overrides, verified recent roots ([EIP-8272](./eip-8272.md)), and post-transaction assertions ([EIP-7906](./eip-7906.md)). It also keeps the capability that lets a dApp take part in selecting the [EIP-7702](./eip-7702.md) account implementation.

The capabilities describe what the dApp wants. The wallet builds the frames. The format of the post-transaction assertions is not defined here: the proposal defines how a named, versioned assertion format is carried and leaves the content to the format.

## Motivation

[EIP-8141](./eip-8141.md) turns a transaction into a list of frames. A wallet that receives a batch of calls through [EIP-5792](./eip-5792.md) decides how many frames to build, which validation to run, who pays, and what is checked after the calls ran. A dApp has no way to influence any of this, although some of these choices depend on what the dApp knows:

- A privacy application knows which nonce key makes its transaction independent of others from the same sender, and which recent root its proof was built against.
- A dApp that sponsors gas knows the paymaster and the data it expects.
- A dApp knows which of its calls must succeed together and which are independent.
- A dApp or a wallet can bound the outcome of a transaction with an on-chain assertion, but only if the assertion reaches the frame list.

An earlier version of this proposal covered the same ground for [ERC-4337](./eip-4337.md) UserOperations. Some of the fields it exchanged, such as `paymasterValidationGasLimit`, do not exist in a frame transaction. Those capabilities are replaced by ones that describe frames. The gas limits and fees keep the field names that wallets already use, with a defined meaning for a frame transaction.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

Terms defined by [EIP-8141](./eip-8141.md), including frame, `VERIFY`, `DEFAULT`, `SENDER`, `APPROVE`, atomic batch, validation prefix and `ENTRY_POINT`, have the meanings given there. The frame names used by its public mempool rules (`deploy`, `self_verify`, `only_verify`, `pay`, `expiry_verify`, `user_op`, `post_op`) are used here as well. `POST_TX` is the frame mode defined by [EIP-7906](./eip-7906.md). `recent_root_verify` is the frame defined by [EIP-8272](./eip-8272.md).

### Scope

These capabilities apply to a `wallet_sendCalls` request on a chain where the wallet builds an EIP-8141 frame transaction for the request. Each call of the request becomes a `SENDER` frame whose `target`, `value` and `data` are the call's `to`, `value` and `data`, and the transaction `sender` is the request's `from`. A call without `to` cannot be expressed this way, because a frame without a target addresses the sender. This proposal does not define how a wallet handles such a call.

A capability is batch-scope unless it is marked call-scope below. Hex quantities follow the encoding rules of [EIP-5792](./eip-5792.md). As in EIP-5792, the dApp marks a capability `optional` if the wallet may ignore it, and a wallet MUST reject a request containing an unsupported capability that is not marked `optional`, with error code `5700`. A request whose capability parameters do not match the interface below, or violate a MUST in this section, is rejected with error code `-32602`.

The wallet chooses everything these capabilities do not specify: the validation frames, who pays when no paymaster is given, and the gas limits and fees that `gasParamsOverride` does not set.

### Capabilities

#### EIP-7702 Authorization Capability

Identifier: `eip7702Auth`

Asks the wallet to make sure the account is delegated to a given smart account implementation.

```typescript
type Eip7702AuthCapabilityParams = {
  delegation: string,      // an address, or the name of an implementation the wallet knows
  version?: string,        // version of the named implementation
  account?: `0x${string}`, // EOA to delegate; defaults to the `from` of the request
}
```

`delegation` is either the address of the delegation target or the name of an implementation, such as `ModularAccountV2`. Names are defined by the wallet and reported in `wallet_getCapabilities`. The wallet resolves `delegation` and `version` to the address of a delegation target and MUST reject the request if it cannot, or if the resulting address is not one it accepts. If `delegation` is an address, `version` MAY be omitted, and the wallet MUST reject a `version` that contradicts that address.

The wallet MUST ensure that, before the calls execute, the code of `account` is the [EIP-7702](./eip-7702.md) delegation designator for the resolved target. The rules for choosing the target are:

- If `version` is given, the target is that version of the implementation. If `account` is delegated to a different version or a different implementation, the wallet re-delegates it.
- If `version` is omitted and `account` is already delegated to a version of the requested implementation, the wallet keeps the current delegation and takes no action. The wallet MAY instead use a version it has recorded for the account.
- If `version` is omitted and `account` is not delegated, or is delegated to something other than the requested implementation, the wallet delegates it to its default version of the implementation.

When a delegation is needed, the wallet signs an authorization for the target and submits it in an [EIP-7702](./eip-7702.md) set-code transaction.

If `delegation` is the zero address, the wallet removes the delegation of `account` by authorizing the zero address. `version` MUST NOT be given in this case. The request MAY have an empty `calls` array, and then the removal is the only effect of the request.

Because the value of a capability in [EIP-5792](./eip-5792.md) is an object, the form above is the one dApps send. A wallet MAY also accept the value `true` and treat it as a request for implicit delegation: the wallet chooses the implementation and version by the rules above for an omitted `version`. A dApp SHOULD NOT send `true` to a wallet that does not say that it accepts it.

An EIP-8141 frame transaction has no authorization list. When the calls are sent as a frame transaction, the set-code transaction is therefore a separate transaction that the wallet submits first. It is not part of the atomic unit, in the same way as the upgrade of an atomic-ready wallet in [EIP-5792](./eip-5792.md): the calls are still executed atomically if `atomicRequired` is `true`, and logs of the set-code transaction MUST NOT be reported as logs of the calls.

The name `eip7702Auth` is unrelated to the field of the same name in an [ERC-4337](./eip-4337.md) UserOperation.

#### Validity Time Limit Capability

Identifier: `validityTimeRange`

Asks the wallet to make the transaction invalid after a given time.

```typescript
type ValidityTimeRangeCapabilityParams = {
  validUntil: `0x${string}`, // the transaction is valid only until this timestamp, in seconds
}
```

The wallet MUST add an `expiry_verify` frame to the transaction as defined by [EIP-8141](./eip-8141.md): mode `VERIFY`, target `EXPIRY_VERIFIER`, `flags` `0`, `value` `0`, state gas limit `0`, and `data` set to `validUntil` as an 8-byte unsigned big-endian integer. This frame MUST be the first frame of the transaction. The wallet MUST reject a `validUntil` that does not fit in 8 bytes.

The wallet MUST verify that `validUntil` is in the future, and MUST present it to the user in a human-readable form.

A lower bound on validity (`validAfter`) was part of the previous version of this proposal. EIP-8141 has no frame for it and this proposal does not carry it.

#### Keyed Nonce Capability

Identifier: `keyedNonce`

Asks the wallet to use [EIP-8250](./eip-8250.md) nonce keys for the transaction.

```typescript
type KeyedNonceCapabilityParams = {
  nonceKeys: `0x${string}`[], // nonce keys, each a uint256
  nonceSeq?: `0x${string}`,   // shared sequence number, a uint64
}
```

The wallet MUST set `nonce_keys` of the transaction to `nonceKeys`. The wallet MUST reject `nonceKeys` that EIP-8250 would reject when decoding: more than 16 keys, no keys, keys that are not strictly increasing, or a `0` key in a list that is not `[0]`.

All selected keys share one sequence number, and EIP-8250 requires it to equal the current sequence of every selected key. If `nonceSeq` is given, the wallet MUST use it as `nonce_seq`. If it is omitted, the wallet reads the current sequence of every key and uses it as `nonce_seq`. The wallet MUST reject the request if the keys do not currently share one sequence number.

A key that has never been used has sequence `0`. The first use of a key costs state gas as defined by EIP-8250. The wallet MUST include this cost in the fee estimate it shows to the user.

#### Paymaster Frame Capability

Identifier: `paymasterFrame`

Asks the wallet to have a given paymaster pay for the transaction, with parameters that the dApp already knows.

```typescript
type PaymasterFrameCapabilityParams = {
  paymaster: `0x${string}`,          // the target of the pay frame
  data: `0x${string}`,               // the calldata of the pay frame
  executionGasLimit: `0x${string}`,  // execution gas limit of the pay frame
  stateGasLimit?: `0x${string}`,     // state gas limit of the pay frame; defaults to 0
  postOp?: {
    target: `0x${string}`,
    data: `0x${string}`,
    executionGasLimit: `0x${string}`,
    stateGasLimit?: `0x${string}`,   // defaults to 0
  },
}
```

The wallet MUST add a `pay` frame to the transaction: mode `VERIFY`, `flags` `0x1` (`APPROVE_PAYMENT`), `target` `paymaster`, `value` `0`, and `data` and gas limits as given. The `pay` frame MUST follow the frame that approves execution for the sender. If `postOp` is given, the wallet MUST add a `post_op` frame: mode `DEFAULT`, `flags` `0`, `value` `0`, with the target, data and limits as given. It MUST be placed after all `SENDER` frames and before any `POST_TX` frame.

The signature hash of a frame transaction covers every frame, so the dApp cannot produce data that includes a signature over the final transaction. The capability is therefore usable only with paymasters whose approval does not depend on a signature over the transaction the wallet assembles. This is the reason for the capability's static form. A request that lets the wallet obtain such data from a paymaster service after the frames are known is not defined here.

The wallet MUST show the user which account pays for the transaction.

A transaction is eligible for the public mempool only under the paymaster rules of EIP-8141. A wallet that accepts a paymaster outside these rules SHOULD tell the user that the transaction may not propagate.

#### Atomic Group Capability

Identifier: `atomicGroup`

This is a call-scope capability. It places calls in groups that succeed or fail together.

```typescript
type AtomicGroupCapabilityParams = {
  id: number, // non-negative integer naming the group
}
```

Calls with the same `id` form one group. The calls of a group MUST be adjacent in the request; the wallet MUST reject a request in which they are not. The wallet MUST set `ATOMIC_BATCH_FLAG` on every `SENDER` frame of a group except the last one, so that the group is an atomic batch as defined by EIP-8141. A group of one call has no effect. Calls without this capability are independent: if the frame of such a call reverts, only that frame is reverted, and the frames after it still execute.

Frames of a group MUST NOT carry approval scope flags, and the wallet MUST NOT place the flag on a frame that EIP-8141 or EIP-7906 forbids it on, namely a `VERIFY` frame, the last frame of the transaction, or a frame directly before a `POST_TX` frame. Calls always become `SENDER` frames that precede the `POST_TX` frames, so these rules hold by construction as long as the layout below is followed.

If `atomicRequired` is `true`, the request MUST either contain no `atomicGroup` capability or place all calls in one group; otherwise the wallet MUST reject it. If `atomicRequired` is `false`, groups give partial atomicity and the calls outside any group are independent.

The failure of a group does not affect `POST_TX` frames: they run after the group and see its outcome.

#### Recent Roots Capability

Identifier: `recentRoots`

Asks the wallet to include verified recent roots as defined by [EIP-8272](./eip-8272.md).

```typescript
type RecentRootsCapabilityParams = {
  tuples: {
    sourceId: `0x${string}`, // 32 bytes
    slot: `0x${string}`,     // a uint64
    root: `0x${string}`,     // 32 bytes
  }[],
}
```

The wallet MUST add one `recent_root_verify` frame: mode `VERIFY`, target `RECENT_ROOT_ADDRESS`, `flags` `0`, `value` `0`, state gas limit `0`, and `data` the concatenation, in the given order, of `sourceId`, `slot` as an 8-byte big-endian integer, and `root` for each tuple. The wallet MUST reject a request with no tuples or with more than `MAX_RECENT_ROOT_REFERENCES` tuples.

For each tuple, the wallet MUST check that `slot` is lower than the current slot and that the difference is not larger than `RECENT_ROOT_USABLE_WINDOW`, with the current slot defined as in EIP-8272 for public mempool validation. The wallet SHOULD also check that the tuple matches the state of the recent root contract, because a tuple that does not match makes the transaction invalid.

The frame is placed as described in the layout below. The capability does not tell the wallet which contract consumes the tuples. A tuple only shows that a root source wrote the root in that slot. Whether a source is trustworthy is up to the contract that uses the root.

#### Post-Transaction Assertions Capability

Identifier: `postTxAssertions`

Asks the wallet to add assertions that run after the calls, as `POST_TX` frames of [EIP-7906](./eip-7906.md).

```typescript
type PostTxAssertionsCapabilityParams = {
  entries: {
    format: { name: string, version: string },
    assertions: unknown,
  }[],
}
```

This proposal does not define what `assertions` contains. Every entry names the format that interprets it. A format is identified by `{ name, version }`. A change of what a format does with `assertions` requires a new version.

A specification of an assertion format MUST define:

1. the schema of `assertions`;
2. a deterministic mapping from `assertions` to an ordered list of `POST_TX` frames, giving each frame its `target`, `data` and execution gas limit, so that two wallets produce the same frames for the same request;
3. what the wallet shows the user for the entry;
4. rules for compatibility between versions.

The wallet maps each entry with the format specification and appends the resulting frames to the end of the transaction, in the order of the entries. A request MAY contain several entries, including several entries of the same format. A frame produced by a format MUST be a `POST_TX` frame. The wallet MUST reject the request if an entry names a format or version it does not support. The `optional` flag of the capability applies to the whole capability: if the dApp marked it `optional`, a wallet that does not support the capability at all ignores it, but a wallet that supports the capability MUST NOT drop an entry silently.

The wallet MAY add `POST_TX` frames of its own after the frames of the dApp. It MUST NOT remove or reorder the frames the entries produce.

#### Gas Parameters Override Capability

Identifier: `gasParamsOverride`

Asks the wallet to use the gas limits and fees given by the dApp in place of its own estimates.

```typescript
type GasValue = `0x${string}` | { multiplier: number }

type GasParamsOverrideCapabilityParams = {
  preVerificationGas?: GasValue,
  verificationGasLimit?: GasValue,
  deploymentGasLimit?: GasValue,
  callGasLimit?: GasValue,
  paymasterVerificationGasLimit?: GasValue,
  paymasterPostOpGasLimit?: GasValue,
  maxFeePerGas?: GasValue,
  maxPriorityFeePerGas?: GasValue,
}
```

All fields are optional. Only the values that the dApp wants to override are given.

A hex value is an absolute value. A `{ multiplier }` is a positive number that scales the wallet's own estimate of the same value. The wallet rounds the scaled value up. The wallet MUST reject a `multiplier` that is not a positive finite number.

The field names are those of an [ERC-4337](./eip-4337.md) UserOperation. For a frame transaction, the wallet applies them as follows. A gas limit sets the execution gas limit of the frames named. The state gas limit of a frame is not affected.

| Field | Applies to |
|---|---|
| `callGasLimit` | The total of the execution gas limits of the `SENDER` frames built from the calls. The wallet divides the total between those frames. |
| `verificationGasLimit` | The execution gas limit of the validation frame of the sender. |
| `deploymentGasLimit` | The execution gas limit of the `deploy` frame. |
| `paymasterVerificationGasLimit` | The execution gas limit of the `pay` frame. |
| `paymasterPostOpGasLimit` | The execution gas limit of the `post_op` frame. |
| `maxFeePerGas` | `max_fee_per_gas` of the transaction. |
| `maxPriorityFeePerGas` | `max_priority_fee_per_gas` of the transaction. |
| `preVerificationGas` | Nothing. A wallet that builds a frame transaction ignores it, because the intrinsic gas of a frame transaction is computed by the protocol. |

`deploymentGasLimit` is not part of an ERC-4337 UserOperation, where `verificationGasLimit` covers the deployment of the account as well. A wallet that builds UserOperations does not enforce `deploymentGasLimit`.

A field that applies to a frame the transaction does not have, such as `paymasterPostOpGasLimit` without a `post_op` frame or `deploymentGasLimit` for an account that already exists, has no effect. The `expiry_verify`, `recent_root_verify` and `POST_TX` frames are not affected by this capability.

The wallet MUST reject a request whose overrides make the transaction invalid under [EIP-8141](./eip-8141.md), for example because the total gas exceeds the limit of a single transaction. The wallet SHOULD warn the user about the overrides in the request and MAY reject a request whose overrides conflict with each other or with other capabilities.

### Frame Layout

The wallet builds the frames of a request in this order. Frames in brackets are present only when needed.

```
[expiry_verify] [recent_root_verify] [deploy] <validation of the sender> [pay]
<SENDER frames of the calls, with atomic batch flags from atomicGroup>
[post_op]
[POST_TX frames]
```

The wallet MUST ensure that:

- there is at most one `expiry_verify` frame, and if present it is the first frame;
- there is at most one `recent_root_verify` frame, and it comes immediately after the `expiry_verify` frame if there is one, and before every other frame;
- no `VERIFY` frame follows the validation prefix;
- the `POST_TX` frames form a contiguous suffix of the frame list;
- the number of frames does not exceed `MAX_FRAMES`.

A transaction that follows this layout and uses the paymaster rules of EIP-8141 is eligible for the public mempool, if the sender validation is also one of the shapes that EIP-8141 recognizes.

### Capability Discovery

A wallet reports each capability it supports in the result of `wallet_getCapabilities`, under the identifier of the capability. The result of every capability in this proposal is an object with a `supported` field. A capability that is absent from the result, or reported with `supported` set to `false`, is not supported.

```typescript
type CapabilitySupport = {
  supported: boolean,
}
type Eip7702AuthSupport = CapabilitySupport & {
  // accepted delegation targets; if absent, the wallet decides per request
  delegations?: {
    name?: string,        // implementation name usable as `delegation`
    version?: string,     // version of the named implementation
    address: `0x${string}`, // the zero address is listed if the wallet accepts removal of a delegation
  }[],
}
type ValidityTimeRangeSupport = CapabilitySupport
type KeyedNonceSupport = CapabilitySupport & {
  maxKeys: `0x${string}`,
}
type PaymasterFrameSupport = CapabilitySupport & {
  postOp: boolean,
}
type AtomicGroupSupport = CapabilitySupport
type GasParamsOverrideSupport = CapabilitySupport
type RecentRootsSupport = CapabilitySupport & {
  maxTuples: `0x${string}`,
}
type PostTxAssertionsSupport = CapabilitySupport & {
  formats: { name: string, versions: string[] }[],
  maxFrames: `0x${string}`, // the largest number of POST_TX frames the wallet adds
}
```

`atomicGroup` relies on the wallet building a frame transaction. A wallet that reports it SHOULD also report the `atomic` capability of [EIP-5792](./eip-5792.md) as `supported`.

## Rationale

### Why this proposal is changed in place

The earlier version of this proposal was never finalized. The capabilities it kept for ERC-4337 describe fields that a frame transaction does not have. Keeping that version next to a new one would double the text to maintain for a proposal that has little adoption. `eip7702Auth` is the exception, and it is kept.

### Replaced and removed capabilities

`staticPaymasterConfiguration` and `multiDimensionalNonce` carried ERC-4337 fields and are replaced by `paymasterFrame` and `keyedNonce`. `validAfter` is removed because EIP-8141 has no canonical frame that enforces it.

### Gas parameters override

`accountAbstractionGasParamsOverride` is renamed `gasParamsOverride`, with the fields and the `{ multiplier }` value form that a deployed implementation already uses. A multiplier lets a dApp say "more than you estimate" without knowing the estimate. That was proposed during review of the first version of this proposal.

The fields keep their ERC-4337 names so that a dApp can send one request to wallets that build UserOperations and to wallets that build frame transactions. A frame transaction has no `preVerificationGas`, and its call gas belongs to several frames, so the table maps each field to the frames it stands for and divides the call total between them. The dApp addresses the phases it knows from ERC-4337, and the wallet decides how many frames they become.

Account deployment is the one phase that differs. In ERC-4337, `verificationGasLimit` includes it. In a frame transaction it is a frame of its own, so `deploymentGasLimit` is added. A dApp that sets `verificationGasLimit` for a request that deploys the account gets the 4337 meaning from a wallet that builds UserOperations and the validation-only meaning from a wallet that builds frames. The dApp should set `deploymentGasLimit` as well, and a wallet that builds UserOperations ignores it.

A limit for one call is a different thing and is not part of this capability. A call is one `SENDER` frame, so such a limit can be addressed. A separate draft proposal defines it as the `gasLimitOverride` capability.

### `eip7702Auth` and EIP-8141

EIP-8141 has no authorization list, because it aims to leave the ECDSA-based authorization of EIP-7702 behind. A dApp that asks for a delegation therefore can no longer count on it being part of the same transaction. The capability keeps its meaning, "the account is delegated to this implementation when the calls run", and leaves the wallet free to meet it with a separate transaction. The parameters follow the form that a deployed implementation of the capability already uses: `account`, a `delegation` that is an address or an implementation name, and a `version`. The rules for omitted and explicit versions, the zero address as the way to remove a delegation, and the `true` shorthand also come from that implementation. Its `supported` field in the capability discovery result is adopted for every capability in this proposal. Names stay wallet-defined, and `wallet_getCapabilities` lets the dApp find out which ones a wallet accepts.

### Atomic groups instead of flow control

[EIP-7867](./eip-7867.md) describes failure handling per call (`rollback`, `halt`, `continue`) and atomicity levels (`strict`, `loose`, `none`). It was written against an earlier version of EIP-5792, and several of the requirements it removes are no longer in EIP-5792. Its atomicity levels differ only when a reorg splits a batch, which cannot happen inside one transaction. Its `rollback` rolls back the whole batch, so it cannot express several independent atomic groups, which is what an EIP-8141 atomic batch is. `halt`, stopping after a failure, has no counterpart in EIP-8141.

Group identifiers are used instead of a flag on a call that means "atomic with the next call". A flag can be set on the last call of a request and describe nothing. A group cannot be malformed in that way, and the request reads as the groups the dApp means.

Calls outside any group are independent because that is how frames behave. A dApp that needs a later call to run only after an earlier call succeeded uses `atomicRequired`.

### Format-agnostic assertions

The content of an assertion, such as which balance bounds or which events to check, is not needed to carry it. Fixing a format here would tie the lifecycle of the format to the lifecycle of the capability. With a named and versioned format, wallets can support several formats, new formats do not require a change to this proposal, and a wallet can reject a format it does not understand instead of misreading it.

The format has to define the mapping to frames so that the signed transaction does not depend on the wallet. EIP-7906 recommends that assertions take their reference values from the `data` of the `POST_TX` frame, which the transaction signature commits to. The mapping is where a format does that.

### Keys and sequence number

EIP-8250 has one sequence number for all keys of a transaction. The capability mirrors that and allows the wallet to read the sequence number from the state, because a dApp that picks keys usually does not know it.

### Static paymaster

A pay frame is validated before the calls and can depend on the whole frame list, including a signature over it. A dApp that passes `data` without knowing the final frames can only support paymasters that do not need such a signature. The ERC-4337 version of this proposal had the same limit and left the dynamic case to [ERC-7677](./eip-7677.md). ERC-7677 is specific to ERC-4337 and a counterpart for frames is not part of this proposal.

## Backwards Compatibility

This version removes `staticPaymasterConfiguration` and `multiDimensionalNonce`, renames `accountAbstractionGasParamsOverride` to `gasParamsOverride` and lets its fields be multipliers, and `validityTimeRange` no longer accepts `validAfter`. A wallet that implemented these capabilities for ERC-4337 UserOperations keeps working for requests it sends as UserOperations, but those requests are no longer described by this proposal.

`eip7702Auth` now takes the parameters that the deployed implementation uses: `delegation` may be an implementation name as well as an address, and `version` is new. The earlier version of this proposal required `account`, which is now optional. Requests in the earlier form, with an address `delegation` and an `account`, remain valid. The type given in the earlier version was malformed, and the type above is the one that matches its description. A zero address `delegation` was not meaningful before and now removes the delegation.

## Security Considerations

### `eip7702Auth`

This is the most sensitive capability in the document. There is no limit to the damage that can be done by signing the wrong authorization.

Wallets MUST take extreme care when working with [EIP-7702](./eip-7702.md). Wallets MUST maintain a strict shortlist of well-known and publicly audited smart account implementations that are acceptable as `delegation`, and every name and version a wallet accepts MUST resolve to an address on that shortlist. A vulnerability or malicious code in the delegation target can drain the whole `account`.

Because the delegation is a separate transaction, it takes effect even if the calls are later rejected by the user or fail. The wallet MUST ask the user to confirm the delegation separately from the calls.

A `version` that differs from the current delegation makes the wallet replace the code of an account that works today. A dApp can use this to move an account to a version the user did not choose. The same happens without a `version` when the account is delegated to something other than the requested implementation. The wallet MUST show the user the current and the new implementation and version whenever it changes a delegation, and MUST do the same when a zero address `delegation` removes one.

### `paymasterFrame`

The pay frame is validated in a static context, so its `data` cannot move assets by itself. The `postOp` frame executes in a non-static context, and its target and data are chosen by the dApp. A post-op call can reach a paymaster that holds token approvals from the user, such as a token paymaster that collects its fee after the calls, and make it spend those approvals. The wallet MUST check that the `postOp` call corresponds to what the user agreed to, in the same way it checks the `calldata` of any other transaction.

### `keyedNonce`

The nonce keys are public and permanent. A dApp that derives a key from private information makes it visible. Each new key costs state gas that the payer is charged, up to 16 keys per transaction. A dApp could choose keys to increase the cost for the user. The wallet MUST include this cost in the displayed fee.

Transactions with overlapping key sets from the same sender depend on each other's sequence numbers. A dApp that reuses a key across unrelated transactions loses the independence that keys are meant to provide.

### `gasParamsOverride`

Limits that are too low make calls or validation fail. A transaction whose validation runs out of gas is invalid, and one whose calls run out of gas reverts and still costs the payer the gas it used. Limits and fees that are too high raise the maximum cost that the payer must be able to cover, and can make a sponsor reject or refuse the transaction. The wallet SHOULD warn the user about overrides that look too low or too high against its own estimate.

A multiplier is applied to the wallet's estimate. A dApp that sends a large multiplier can raise the maximum cost without a visible absolute value, so the wallet MUST show the resulting values, not the request.

### `atomicGroup`

A dApp that assumes that later calls only run after earlier calls succeeded gets the opposite for ungrouped calls: a failed call is reverted alone and the following calls still execute. A dApp that depends on the order of success MUST use `atomicRequired` or a group.

### `recentRoots`

The tuples are not trusted by the wallet. A tuple shows only that a source wrote a value in a slot. The wallet MUST NOT describe a root as verified information about the content it commits to.

A tuple that was valid when the wallet built the transaction may stop being valid before inclusion, because the usable window ends or because a reorg removes the entry. The transaction is then invalid, not reverted, and the user pays nothing, but it will not execute. A dApp SHOULD combine `recentRoots` with `validityTimeRange`.

### `postTxAssertions`

The security considerations of [EIP-7906](./eip-7906.md) apply to every assertion format. Three of them matter most here.

- An assertion that checks too little is worse than no assertion, because it gives a false sense of safety. The wallet SHOULD only advertise a format whose checks it can describe to the user.
- A `POST_TX` failure reverts only the execution body. The validation prefix, including the payment of gas, stays. An assertion that fails costs the user the gas of the transaction. A hostile dApp can use assertions to waste a user's gas, but it cannot use them to move assets. A wallet MAY therefore accept assertions from a dApp it does not trust, but they only add to the protection of the user. The wallet MUST NOT replace its own assertions with those of the dApp.
- Silently dropping an assertion is the dangerous failure. The wallet MUST reject a request whose assertions it cannot include. A wallet may ignore an `optional` capability only if it does not support the capability at all.

A dApp that requires its assertion in every transaction of an account, rather than in one request, cannot do that through this capability. EIP-7906 describes how an account enforces a `POST_TX` frame in its own validation.
