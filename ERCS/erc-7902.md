## Abstract


[EIP-8141](./eip-8141.md) and its extensions define a new [EIP-2718](./eip-2718.md) transaction type for account abstraction with a rich and innovative set of features. The wallets adopting EIP-8141 must have a mechanism to expose these features to their users and applications. Previously, a limited subset of these features has been available through [ERC-4337](./eip-4337.md) UserOperations

[EIP-5792](./eip-5792.md) defines a JSON-RPC API for communication between wallets and dApps, and allows the API be extended with "capabilities".

This proposal defines capabilities that a wallet can implement to expose the features of an [EIP-8141](./eip-8141.md) frame transaction to dApps: an expiring time limit on validity, keyed nonces ([EIP-8250](./eip-8250.md)), a sponsored gas payment, atomic batching, per-frame gas limit and fee overrides, verified recent roots ([EIP-8272](./eip-8272.md)), and post-transaction assertions ([EIP-7906](./eip-7906.md)). It also defines the capability that allows a dApp take part in suggesting the [EIP-7702](./eip-7702.md) account implementation.

## Motivation

[EIP-8141](./eip-8141.md) turns a transaction into a list of frames. A wallet that receives a batch of calls through [EIP-5792](./eip-5792.md) decides how many frames to build, which validation to run, who pays, and what is checked after the calls ran. A dApp has no way to influence any of this, although some of these choices depend on what the dApp knows:

- A privacy application knows which nonce key makes its transaction independent of others from the same sender, and which recent root its proof was built against.
- A dApp that sponsors gas knows the paymaster and the data it expects.
- A dApp knows which of its calls must succeed together and which are independent.
- A dApp or a wallet can bound the outcome of a transaction with an on-chain assertion, but only if the assertion reaches the frame list.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

Terms defined by [EIP-8141](./eip-8141.md), including frame, `VERIFY`, `DEFAULT`, `SENDER`, `APPROVE`, atomic batch, validation prefix and `ENTRY_POINT`, have the meanings given there. The frame names used by its public mempool rules (`deploy`, `self_verify`, `only_verify`, `pay`, `expiry_verify`, `user_op`, `post_op`) are used here as well. `ASSERT` is the frame mode defined by [EIP-7906](./eip-7906.md). `recent_root_verify` is the frame defined by [EIP-8272](./eip-8272.md).

### Scope

These capabilities apply to a `wallet_sendCalls` request on a chain where the wallet builds an EIP-8141 frame transaction for the request. The transaction `sender` is the `from` of the request.
Every call of the request MUST specify `to`. The wallet MUST reject a request with a call that does not, because a frame without a target addresses the sender and cannot express contract creation.
The wallet MAY choose everything that capabilities did not explicitly specify.

### Call Dispatch

By default, this specification does not say which frames carry the calls. The wallet decides how the account executes each call. It may build a `SENDER` frame whose `target`, `value` and `data` are the `to`, `value` and `data` of the call. It may also build a `DEFAULT` frame that calls the execution function of the account, with the call encoded in the calldata. A wallet whose account policy does not allow `SENDER` frames uses the second form.

Whichever form the wallet chooses, it MUST preserve the outcomes that the request describes:

- the calls execute in the order of the request;
- the calls of an atomic batch succeed or fail together;
- a call outside an atomic batch does not change the outcome of any other call: if it reverts, the other calls still execute.

A wallet MAY combine adjacent calls in one frame only if they belong to the same atomic batch, or if none of them belongs to an atomic batch. It MUST NOT combine calls across the boundary of an atomic batch, and it MUST NOT combine a call that carries the `callFrame` capability. A wallet that combines independent calls MUST use execution semantics under which the failure of one call does not revert the others.

### Capabilities

#### EIP-7702 Authorization Capability

Identifier: `eip7702Auth`

Asks the wallet to make sure the account is delegated to a given smart account implementation.

```typescript
type Eip7702AuthCapabilityParams = {
  delegation: string,      // an address or a name of an implementation the wallet knows
  version?: string,        // version of the named implementation
  account?: `0x${string}`, // EOA authorizing the delegation, defaulting to the `from` of the request
}
```

`delegation` is either the address of the delegation target or a wallet-supplied well-known name of an implementation.
Names are defined by the wallet and reported in `wallet_getCapabilities`.
The wallet resolves `delegation` and `version` to the address of a delegation target and MUST reject the request if it does not recognize the named `delegation` target or if the `delegation` address is not one it accepts.
If `delegation` is an address, `version` MUST be omitted.
The wallet SHOULD reject signing the authorization if the specified `delegation` address is not verified to be safe. 

The wallet MUST ensure that, before the calls execute, the code of `account` is the [EIP-7702](./eip-7702.md) delegation designator for the resolved target.

The target MUST be chosen according to the following rules:

- If `account` is already delegated to any implementation different from the specified one, the wallet re-delegates the account.
- If `version` is given and `delegation` is a known implementation name, the target is that version of that implementation.
- If `version` is omitted and `account` is already delegated to any version of the requested implementation, the wallet takes no action and the account keeps the current delegation.

When a delegation is needed, the wallet signs an authorization for the target and submits it in an [EIP-7702](./eip-7702.md) set-code transaction.

Applications request the removal of the delegation of `account` by authorizing a `delegation` to the zero address.

An EIP-8141 frame transaction has no authorization list. When the calls are sent as a frame transaction, the set-code transaction is therefore a separate transaction that the wallet submits first. It is not part of the atomic unit, and logs of the set-code transaction MUST NOT be reported as logs of the calls.

#### Validity Time Limit Capability

Identifier: `validityTimeRange`

Asks the wallet to make the transaction invalid after a given time.

```typescript
type ValidityTimeRangeCapabilityParams = {
  validUntil: `0x${string}`, // the transaction is valid only until this timestamp, in seconds
}
```

The wallet MUST add an `expiry_verify` frame to the transaction as defined by [EIP-8141](./eip-8141.md): mode `VERIFY`, target `EXPIRY_VERIFIER`, `flags` `0`, `value` `0`, state gas limit `0`, and `data` set to `validUntil` as an 8-byte unsigned big-endian integer. This frame MUST be the first frame of the transaction. The wallet MUST reject a `validUntil` that does not fit in 8 bytes.

The wallet MUST verify that `validUntil` is in the future, and MUST present it to the user in a human-readable form.

#### Keyed Nonce Capability

Identifier: `keyedNonce`

Asks the wallet to use [EIP-8250](./eip-8250.md) nonce keys for the transaction.

```typescript
type KeyedNonceCapabilityParams = {
  nonceKeys: `0x${string}`[], // nonce keys, each a uint256
  nonceSeq?: `0x${string}`,   // shared sequence number, a uint64
}
```

The wallet MUST set `nonce_keys` of the transaction to `nonceKeys`.

The wallet MUST reject `nonceKeys` that violate EIP-8250 definitions of valid nonce keys array, i.e. more than 16 keys, no keys, keys provided out of order, or a `0` key in a list that is not `[0]`.

All selected keys share one sequence number, and EIP-8250 requires it to equal the current sequence of every selected key.

If `nonceSeq` is given, the wallet MUST use it as `nonce_seq`.

If `nonceSeq` is omitted, the wallet reads the current sequence of every key and uses it as `nonce_seq`.
The wallet MUST reject the request if the keys do not currently share one sequence number.

The wallet MUST include correct estimates for the gas cost of incrementing all the specified nonce keys in the fee estimate it presents to the user.

#### Paymaster Frame Capability

Identifier: `paymasterFrame`

Asks the wallet to have a given "Paymaster" contract accept the payment for the transaction with parameters provided by the application.

```typescript
type PaymasterFrameCapabilityParams = {
  paymaster: `0x${string}`,          // the target of the pay frame
  data: `0x${string}`,               // the calldata of the pay frame
  executionGasLimit: `0x${string}`,  // execution gas limit of the pay frame
}
```

The wallet MUST add a `pay` frame to the transaction: mode `VERIFY 0x1` (`APPROVE_PAYMENT`), to the `paymaster` address with `data` and gas limits as specified in the request.

The `pay` frame MUST follow the frame that approves execution for the sender.

The signature hash of a frame transaction covers every frame, so the dApp cannot produce data that includes a signature over the final transaction. The capability is therefore usable only with paymasters whose approval does not depend on a signature over the transaction the wallet assembles.

A transaction is eligible for the canonical public mempool only under the mempool validation rules of EIP-8141.
A wallet that decides to accept paymasters outside these rules MUST tell the user that the transaction may not propagate.

#### Atomic Group Capability

Identifier: `atomicGroup`

This is a call-scope capability. It places calls in groups that succeed or fail together.

```typescript
type AtomicGroupCapabilityParams = {
  id: number, // non-negative integer naming the group
}
```

Calls with the same `id` form one group. The calls of a group MUST be adjacent in the request. The wallet MUST set `ATOMIC_BATCH_FLAG` on every specified frame of a group except the last one, creating an atomic batch as defined by EIP-8141. A group of one call has no effect. Calls without this capability are independent: if the frame of such a call reverts, only that frame is reverted, and the frames after it still execute.

The wallet MUST reject a call request that specifies a batch layout that violates the specification of the underlying EIP-8141 batching mechanism, for example using calls of the group that not adjacent.

The `atomicRequired` filed MUST be set to `false` when using the `atomicGroup` capability, or the request MUST be rejected.

#### Call Frame Capability

Identifier: `callFrame`

This is a call-scope capability. It overrides the choice of the frame for one call, which the wallet otherwise makes as described in [Call Dispatch](#call-dispatch).

```typescript
type CallFrameCapabilityParams = {
  mode: "SENDER" | "DEFAULT",
}
```

- `SENDER`: the wallet MUST build one `SENDER` frame whose `target`, `value` and `data` are the `to`, `value` and `data` of the call.
- `DEFAULT`: the wallet MUST build one `DEFAULT` frame whose `target` is `to` and whose calldata is `data`, without wrapping the call. The `value` of the call MUST be absent or zero, because only `SENDER` frames carry value. The wallet MUST reject the request otherwise.

The frame of a call that carries this capability is the only frame of that call. It may be part of an atomic batch.

If the wallet cannot build the requested frame, for example because the policy of the account does not allow `SENDER` frames, it MUST reject the request, unless the capability is marked `optional`. In that case the wallet ignores the capability and dispatches the call as it would without it.

#### Recent Roots Capability

Identifier: `recentRoots`

Asks the wallet to include verified recent roots as defined by [EIP-8272](./eip-8272.md).

```typescript
type RecentRootsCapabilityParams = {
  tuples: {
    sourceId: `0x${string}`, // bytes32
    slot: `0x${string}`,     // uint64
    root: `0x${string}`,     // bytes32
  }[],
}
```

The wallet MUST add one `recent_root_verify` frame: mode `VERIFY`, target `RECENT_ROOT_ADDRESS`, `flags` `0`, `value` `0`, state gas limit `0`, and `data` the concatenation, in the given order, of `sourceId`, `slot` as an 8-byte big-endian integer, and `root` for each tuple. The wallet MUST reject a request with no tuples or with more than `MAX_RECENT_ROOT_REFERENCES` tuples.

For each tuple, the wallet MUST check that `slot` is lower than the current slot and that the difference is not larger than `RECENT_ROOT_USABLE_WINDOW`, with the current slot defined as in EIP-8272 for public mempool validation.

#### Post-Transaction Outcome Assertions Capability

Identifier: `outcomeAssertions`

Asks the wallet to add assertions that run after the calls, as `ASSERT` frames of [EIP-7906](./eip-7906.md).

```typescript
type PostTxAssertionsCapabilityParams = {
  entries: {
    assertionsFormat: string,
    assertions: unknown,
  }[],
}
```

This proposal does not define what `assertions` contains. Every entry names the format that interprets it. A format is identified by the unique versioned string identifier, specified as `assertionsFormat`.

A specification of an assertion format is outside the scope of this document.

The wallet maps each entry with the format specification and appends the resulting frames to the end of the transaction.
A frame produced by a format MUST be an `ASSERT` frame. The wallet MUST reject the request if an entry names a format or version it does not support.

The wallet MAY add `ASSERT` frames of its own after the frames requested by the application.
The wallet MUST NOT remove or reorder the frames requested by the application.

### Frame Layout

The wallet builds the frames of a request in this order. Frames in brackets are optional and are present only when requested.

```
[expiry_verify] [recent_root_verify] [deploy] <validation of the sender> [pay]
<frames of the calls, with atomic batch flags from atomicGroup>
[ASSERT frames]
```

The wallet MUST ensure that:

- there is at most one `expiry_verify` frame, and if present it is the first frame;
- there is at most one `recent_root_verify` frame, and it comes immediately after the `expiry_verify` frame if there is one, and before every other frame;
- no `VERIFY` frame follows the validation prefix;
- the `ASSERT` frames form a contiguous suffix of the frame list;
- the number of frames does not exceed `MAX_FRAMES`.

This ensures that a transaction that follows this layout and uses the paymaster rules of EIP-8141 is eligible for the canonical public mempool, as long as the validation prefix is compliant with the appropriate mempool rules.

## Rationale

### `eip7702Auth` and EIP-8141

EIP-8141 has no authorization list. A dApp that asks for a delegation therefore can no longer count on it being part of the same transaction.

The capability keeps its meaning, "the account is delegated to this implementation when the calls run", and leaves the wallet free to meet it with a separate transaction. The parameters follow the form that deployed implementations of the capability already use.

### Format-agnostic assertions

Defining the exact content of an assertion request, such as which balance bounds or which events to check, is not needed for the definition of the `outcomeAssertions` capability. Fixing a format here would tie the lifecycle of the format to the lifecycle of the capability. With a named and versioned format, wallets can support several formats, new formats do not require a change to this proposal, and a wallet can reject a format it does not understand instead of misreading it.

The format has to define the mapping to frames so that the signed transaction does not depend on the wallet. EIP-7906 recommends that assertions take their reference values from the `data` of the `ASSERT` frame, which the transaction signature commits to.

### Static paymaster

A pay frame is validated before the calls and can depend on the whole frame list, including a signature over it. A dApp that passes `data` without knowing the final frames can only support paymasters that do not need such a signature. The ERC-4337 version of this proposal had the same limit and left the dynamic case to [ERC-7677](./eip-7677.md). ERC-7677 is specific to ERC-4337 and a counterpart for frames is not part of this proposal.

## Backwards Compatibility

Wallet and applications that implemented support for ERC-4337 UserOperations are expected to upgrade to EIP-8141 over time. 
This includes switching to smart contracts and tooling, including the `wallet_sendCalls` capabilities, designed for EIP-8141 from day one.

## Security Considerations

### `eip7702Auth`

This is the most sensitive capability in the document. There is no limit to the damage that can be done by signing the wrong authorization.

Wallets MUST take extreme care when working with [EIP-7702](./eip-7702.md). Wallets MUST maintain a strict shortlist of well-known and publicly audited smart account implementations that are acceptable as `delegation`, and every name and version a wallet accepts MUST resolve to an address on that shortlist. A vulnerability or malicious code in the delegation target can drain the whole `account`.

Because the delegation is a separate transaction, it takes effect even if the calls are later rejected by the user or fail. The wallet MUST ask the user to confirm the delegation separately from the calls.

A `version` that differs from the current delegation makes the wallet replace the code of an account that works today. A dApp can use this to move an account to a version the user did not choose. The same happens without a `version` when the account is delegated to something other than the requested implementation. The wallet MUST show the user the current and the new implementation and version whenever it changes a delegation, and MUST do the same when a zero address `delegation` removes one.

### `paymasterFrame`

The pay frame is validated in a static context, so its `data` cannot move assets by itself. The `postOp` frame executes in a non-static context, and its target and data are chosen by the dApp. A post-op call can reach a paymaster that holds token approvals from the user, such as a token paymaster that collects its fee after the calls, and make it spend those approvals. The wallet MUST check that the `postOp` call corresponds to what the user agreed to, in the same way it checks the `calldata` of any other transaction.

### `keyedNonce`

The nonce keys are public and permanent. A dApp that derives a key from private information makes it visible. Each new key costs state gas that the payer is charged, up to 16 keys per transaction. A dApp could choose keys to increase the cost for the user. The wallet MUST include this cost in the displayed fee.

Transactions with overlapping key sets from the same sender depend on each other's sequence numbers. A dApp that reuses a key across unrelated transactions loses the independence that keys are meant to provide.

### `gasParamsOverride`

Limits that are too low make calls or validation fail. A transaction whose validation runs out of gas is invalid, and one whose calls run out of gas reverts and still costs the payer the gas it used. Limits and fees that are too high raise the maximum cost that the payer must be able to cover, and can make a sponsor reject or refuse the transaction. The wallet SHOULD warn the user about overrides that look too low or too high against its own estimate.

A multiplier is applied to the wallet's estimate. A dApp that sends a large multiplier can raise the maximum cost without a visible absolute value, so the wallet MUST show the resulting values, not the request.

### `callFrame`

A `DEFAULT` frame is executed with `ENTRY_POINT` as the caller and needs no approval from the sender. With `mode` set to `DEFAULT`, the dApp chooses a target and calldata that run with that caller. This is harmless unless a contract treats `ENTRY_POINT` as an authority on its own. An account that does so lets any transaction trigger its execution function. The wallet MUST show the user the target and the calldata of the frame, and SHOULD decode the inner call when it can.

The target sees the same `msg.sender` whichever mode is used, but `ORIGIN` differs: it is the sender in a `SENDER` frame and `ENTRY_POINT` in a `DEFAULT` frame. A target that reads `tx.origin` can behave differently depending on the frame the wallet chose, and a dApp that depends on it SHOULD set `mode` explicitly.

### `atomicGroup`

A dApp that assumes that later calls only run after earlier calls succeeded gets the opposite for ungrouped calls: a failed call is reverted alone and the following calls still execute. A dApp that depends on the order of success MUST use `atomicRequired` or a group.

### `recentRoots`

The tuples are not trusted by the wallet. A tuple shows only that a source wrote a value in a slot. The wallet MUST NOT describe a root as verified information about the content it commits to.

A tuple that was valid when the wallet built the transaction may stop being valid before inclusion, because the usable window ends or because a reorg removes the entry. The transaction is then invalid, not reverted, and the user pays nothing, but it will not execute. A dApp SHOULD combine `recentRoots` with `validityTimeRange`.

### `postTxAssertions`

The security considerations of [EIP-7906](./eip-7906.md) apply to every assertion format. Three of them matter most here.

- An assertion that checks too little is worse than no assertion, because it gives a false sense of safety. The wallet SHOULD only advertise a format whose checks it can describe to the user.
- A `POST_TX` failure reverts only the execution body. The validation prefix, including the payment of gas, stays. An assertion that fails costs the user the gas of the transaction. A hostile dApp can use assertions to waste a user's gas, but it cannot use them to move assets. A wallet MAY therefore accept assertions from a dApp it does not trust, but they only add to the protection of the user. The wallet MUST NOT replace its own assertions with those of the dApp.
- Silently dropping an assertion is the dangerous failure. The wallet MUST reject a request whose assertions it cannot include. A wallet may ignore an `optional` capability only if it does not support the capability at all.

A dApp that requires its assertion in every transaction of an account, rather than in one request, cannot do that through this capability. EIP-7906 describes how an account enforces a `POST_TX` frame in its own validation.
